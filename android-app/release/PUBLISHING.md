# TIH Learning — publishing handoff

The app is prepared as a learning-only Android companion for existing TIH accounts.
This folder contains review material, not evidence of Play approval or a production deployment.

## Prepared in this repository

- Kotlin / Compose app targeting Android 16 (API 36), minimum Android 8 (API 26).
- All 57 existing courses, their authored documents, questions and local artwork.
- Source-derived organization, support, privacy-rights and relevant terms information.
- Native About, Help, Privacy, Terms and account-deletion-request screens.
- No dashboard, registration, certificate-portal or website-checkout buttons in the app.
  Support opens email, a phone dialer or WhatsApp; learning videos/resources open only on tap.
- No in-app purchases. Existing approved enrollment unlocks courses after authentication.
- Encrypted session tokens; local study records; no advertising or analytics SDK.
- Release shrinking, unsigned AAB assembly, release lint, 16 KB ELF/ZIP checks, device UI
  tests and a startup check using the actual minified release code.
- Store listing, the existing 512px TIH logo, a feature graphic, and standalone app privacy
  and account-deletion pages generated by `node android-app/tools/prepare-store.mjs`.

## 1. Confirm the app identity and owner account

If replacing an existing Play app, get its exact package name, highest uploaded version code,
Play App Signing status and upload-key arrangement from Play Console. An update must preserve
that package identity and use the correct signing setup. Do not create a replacement key blindly.

For a new listing, the proposed package is `org.tolbertinnovationhub.learning`. This remains
provisional until the owner confirms that the listing is new. The preview uses `.preview`.
The owner must complete Play Console account verification and any required production-access process.

Build values can be supplied through the environment:

| Variable | Meaning |
| --- | --- |
| `TIH_APPLICATION_ID` | Owner-confirmed package name; default is the proposed new package |
| `TIH_VERSION_CODE` | Positive integer greater than every previous uploaded version; default 2 |
| `TIH_KEYSTORE_PATH` | Absolute path to the correct upload keystore |
| `TIH_KEYSTORE_PASSWORD` | Keystore password |
| `TIH_KEY_ALIAS` | Upload key alias |
| `TIH_KEY_PASSWORD` | Upload key password |

All four signing variables must be supplied together. Keep them in private local/CI secret
configuration, never in source, messages, store descriptions or shell history. With no signing
variables, the release AAB is intentionally unsigned. Android Studio's Generate Signed Bundle
flow is also available. No production signing key is generated or committed by this project.

After setting the owner configuration, run from `android-app/`:

```sh
./gradlew --no-daemon :app:bundleRelease :app:lintRelease
```

Output: `app/build/outputs/bundle/release/app-release.aab`.
Configure Play App Signing and upload the correctly signed bundle to an internal test first.
The CI release startup check uses a temporary **debug** signature solely to install and test
minified code. Its test APK is not a release artifact or an upload-key substitute.

## 2. Verify the actual backend before allowing real students

The source SQL contains broad `authenticated` policies, for example `stu_all_admin`,
`enr_all_admin` and `ac_admin` using unrestricted conditions. A normal Supabase Auth student
also has the authenticated role. The client cannot repair an unsafe server policy.

Run the read-only `backend-audit.sql` in the authorized project's SQL editor. It lists schema,
policy and function definitions and does not return student records. Review the deployed results,
admin identity/claims and legacy RPCs before designing a migration. **No SQL from this folder
changes production.** Do not apply the existing repository migrations merely to make the app work.

Use approved non-production test accounts to verify active-approved, active-unapproved,
suspended and legacy learners. Check cross-account denial with two distinct users, token expiry,
enrollment revocation, offline expiry and sign-out. Never use a service-role key in the app.
The app selects only `id,name,status` from `student_me` and only its own grant fields; these
filters minimize data but do not substitute for server authorization.

## 3. Publish the accurate privacy and deletion pages

Run from the repository root:

```sh
node android-app/tools/prepare-store.mjs
python3 android-app/tools/render-store.py
```

Review `release/output/app-privacy.html` and `account-deletion.html`, confirm TIH support
actually receives and processes requests, and publish both on a public HTTPS location.
These pages have no purchase links and work without an app login. Enter their final URLs in
Play Console. The app displays the same privacy explanation offline; the website's older,
broader privacy text alone does not describe the Android/Supabase data flow accurately.

The existing TIH policy supplies the contact, deletion right and 30-day response statement.
No new automatic server-deletion endpoint has been invented. The app opens a reviewable email
request; sending it and processing it are separate actions. The owner must verify ownership,
delete eligible account data and explain any required retention. Local deletion and server
deletion are separately explained to learners.

## 4. Complete Play's declarations and store presentation

Use the prepared store text and real device screenshots. Do not use screenshots of test fixtures
as proof of a signed-in production account. The lesson-reader screenshot demonstrates existing
lesson rendering, not a real paid learner test. Use `store-icon-512.png` and the rendered feature
graphic. Store title is TIH Learning; category is Education; support is copied from TIH's site.

Complete Data safety using `DATA-SAFETY.md` as a code-based draft and confirm backend logging.
Declare no ads for this build. Answer the content-rating questionnaire against the actual course
materials and external videos. TIH's current source policy describes programs for ages 16+;
the owner must confirm the real intended audience and any minors' access practices.

Supply a dedicated review account with approved course access and clear app-access instructions
inside Play Console. Do not place credentials in this repository. Confirm rights to offline
distribution of written materials and artwork; APK assets are extractable. YouTube videos remain
links and are not downloaded. Course titles must not be interpreted as promises that app practice
issues an official credential.

## 5. Test and release

Review the CI artifacts and Play pre-launch report. Test real phones, slower connections, large
text, TalkBack, dark mode, process restarts and Android versions used by learners. Fix crashes
and policy findings before production. Personal developer accounts created after November 13,
2023 generally require at least 12 opted-in testers continuously for 14 days before applying for
production access; follow the requirement shown for the actual account.

The owner must approve the final listing, app identity, signing and production rollout.
Google controls review and approval. Do not promise an approval date.

## Product limitations that remain explicit

Progress, notes, bookmarks and practice scores stay on the device. They do not sync to the website
or issue certificates. This is described in the app and listing. Cloud synchronization is a future
backend feature, not a hidden launch claim. The website currently stores aggregate progress, so
safe two-way sync needs a separate reviewed data model and migration.

No merge, website deployment, database mutation or Play submission is performed by this branch.
The website's Pages workflow publishes the repository root: review excluding Android sources
before a future merge as a separate website-deployment change.
